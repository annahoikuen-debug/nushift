## 2. 依存の向き

```
__main__ / streamlit_app / ui
        |
        +--> standards ----+
        +--> solver -------+--> domain <-- local_rules
        +--> gap_analysis -+        ^
        +--> diagnostics --------+
        +--> shift_patterns -------+
        +--> relaxation ----------+
        +--> data_loader -----------+   （domain を import するだけ）
        +--> validation --------------+
        +--> exporter
        +--> sample_data
        +--> gas_client
        +--> local_rules
        +--> config
```

### 依存の原則

1. **`domain` は他のモジュールを `import` しない。ただし他の全モジュールが `domain` に依存する。**
   これは「全モジュールが依存する契約」をコードの形で強制している。

2. **`solver` は `gap_analysis` をモジュールレベルで `import` しない。**
   関数の中で遅延 `import` して検査を呼ぶ:

   ```python
   def _attach_violations(result, requirements, staff, prefs, standard, settings) -> None:
       """gap_analysis の検査結果を SolveResult に載せる（失敗しても致命的ではない）。"""
       try:
           from shiftai import gap_analysis
       except Exception:
           return
   ```

   一方、`gap_analysis` 側は逆にモジュールレベルで `solver` を import している:

   ```python
   from shiftai.solver import month_fraction, staff_work_hours
   ```

   この非対称性の効果は次の 2 つ。

   - `solver` 側の依存が関数の中に閉じているので、モジュールの読み込み順による循環が発生しない
   - `gap_analysis` なしで `solver` だけを単独で使う用途（ベンチマークやライブラリ利用）でも動く

3. **`exporter` は `solver` と `standards` を `import` しない。**
   `SolveResult` / `RequirementTable` / `StaffMember` は `domain` の型だけを受け取る。
   だから出力処理だけを他の場所へ切り出して再利用できる。

4. **`data_loader` は `solver` と `standards` を使わない。**
   読込は「型を作ること」までが責務。「型から計算すること」は `standards` と `solver` の責務。

5. **`gas_client` は `data_loader` と `solver` を使わない。**
   GAS 連携は DataFrame を往復するだけで、園の業務知識を持たない。

### 循環依存を避けた設計

循環依存（dependency cycle）はモジュールが互いに必要になるときに起きる。本プロジェクトは
次の 3 つの工夫でそれを避けている。

| 工夫 | 内容 | 効果 |
| --- | --- | --- |
| 遅延 import | `solver._attach_violations` など関数内でのみ import する | モジュールの読み込み順の制約を排除する |
| 型の一元化 | 層をまたぐ関数の受け渡しを `domain` の型で閉じる | シグネチャが `domain` だけで完結する |
| 一方向の分割 | `standards`（必要人数）と `solver`（配置）の入出力を分離する | 相互参照が生まれる余地をなくす |

**循環依存が起きたときの兆候**: import 時に `ImportError: cannot import name ...` が出る、
`__init__.py` に大量の re-export が必要になる、型注釈が循環する。現在のコードでは起こらない。

## 3. モジュールごとの責務と境界

### `domain`（共通ドメインモデル）

全モジュールが依存する契約（contract）。データクラスと列挙型で構成され、副作用は持たない。
自己完結した計算が 3 つだけ含まれる（`StaffingStandard.headcount_for`、`StaffingStandard.slot_kind`、
`RequirementTable.to_long_dataframe`）。変更の影響は全モジュールに及ぶ。

### `standards`（配置基準エンジン）

- 入力: `ChildPlan` の集合、一園の基準 `StaffingStandard`、開所・閉所時刻、粒度
- 出力: `RequirementTable`（1 日 × 1 時間帯 × 1 年齢クラスの必要人員）
- 境界: **誰がいつ働くかには触れない**。園児数と定員比から必要人数を求めるだけ
- 出力の `Requirement.basis` に算出根拠の日本語文が入る。UI はその文字列をそのまま表示する

### `solver`（MILP 最適化）

- 入力: `RequirementTable`、`StaffMember`、`StaffPreferences`、`FacilitySettings`、`ObjectiveWeights`
- 出力: `SolveResult`（`ShiftDay` の集合、`objective_value`、違反リスト、`stats`）
- 境界: **園児数や定員比をここで再計算しない**。必要な人数は `RequirementTable` から受け取るだけ
- `children` は引数に含むが、統計表示以外の目的では使わない

### `gap_analysis`（検査）

- 入力: `RequirementTable` と `SolveResult`
- 出力: `GapReport`（過不足）と `Violation` のリスト
- 境界: **シフトを計算し直さない**。受け取った `SolveResult` を読み取って照合するだけ

### `local_rules`（自治体プリセット）

`StaffingStandard` の具体的なインスタンスを `MUNICIPAL_PRESETS` として保持し、UI 向けの
説明カード（`LocalRuleNote`）を組み立てる。数値は「目安」であり、自治体の告示・条例の
確認は別途必要（詳細は `03_配置基準と自治体ルール.md`）。

### `data_loader` / `exporter`（入出力）

- `data_loader`: 3 つの DataFrame を `LoadResult` にする。1 行の不正で全体が落ちない設計
- `exporter`: `SolveResult` を CSV / Excel / ICS / ZIP にする。`domain` の型だけを使う

### `validation`（入力表の検証）

- 入力: 3 つの DataFrame（読み込み**前**の生の表）
- 出力: `ValidationReport`（`ValidationIssue` の集合。深刻度は `error` / `warning` の 2 段階）
- 境界: **`data_loader` を import するが、`LoadResult` は作らない。**
  `data_loader` は「不正値を静かに既定値へ置き換えて読み込む」側、
  `validation` は「その値が運用として成立しているか」を利用者に見せる側という役割分担
- 位置づけ: **タブ1（データ投入）で使う。** ここで `error` がある限り読み込みさせない

### `shift_patterns` / `relaxation` / `diagnostics`

- `shift_patterns`: `ShiftPattern`（開始・終了時刻だけを持つ型）と境界判定。
  `domain` と `shift_patterns` 以外の実装詳細には依存しない
- `relaxation`: 段階番号と説明のみ。データを持たない定数モジュール
- `diagnostics`: `solver.shortfall_rows` と `solver.solve_shift` を使って
  「どの日のどの時間帯で何名が不足したか」「どの制約を外せば解けるか」を調べる。
  **CBC を起動するのは利用者が明示的に求めたときだけ**（自動では走らない）

### `ui`（Streamlit 表示層）

- `state.py` がセッション状態を集中管理する
- 各タブは表示のみ。計算は `standards` / `solver` / `gap_analysis` に委譲する
- `components.py` と `theme.py` は見た目の部品

## 4. なぜ `standards` と `solver` を分断したのか

### 分断の構造

```
ChildPlan[]  --->  standards.build_requirements()  --->  RequirementTable
                                                                   |
                                                                   v
                                              solver.solve_shift(requirements, staff, ...)
                                                                   |
                                                                   v
                                                               SolveResult
```

`solver.solve_shift()` のシグネチャ（`src/shiftai/solver.py`）:

```python
def solve_shift(
    children: Sequence[ChildPlan],        # 統計表示用（配置の計算には使わない）
    staff: Sequence[StaffMember],
    requirements: RequirementTable,       # ここが層と層の唯一の境界
    preferences: Mapping[str, StaffPreferences] | None = None,
    weights: ObjectiveWeights | None = None,
    *,
    fixed_assignments: Mapping[tuple[str, date, str], CellState] | None = None,
    settings: FacilitySettings | None = None,
    time_limit_sec: int = 60,
    msg: bool = False,
    standard: StaffingStandard | None = None,
) -> SolveResult:
```

### 分断の理由

1. **配置基準の変更がソルバに波及しない。**
   自治体の基準が改定されても `MUNICIPAL_PRESETS` の数値を書き換えるだけで済む。
   `solver` のコードは 1 行も触らない。園ごとの上乗せを `build_standard(key, overrides)` で
   適用する場合も同様である。

2. **「何人が必要か」と「誰がいつ働くか」は別の問題である。**
   前者は基準表と在園児数という静的な計算、後者は制約付き最適化という動的な探索である。
   分断するとそれぞれのテストが独立に書ける。`tests/test_standards.py` の 30 テストは
   ソルバを 1 回も起動しない。

3. **最適性の範囲が明確になる。**
   一度 `RequirementTable` に「必要人員」として固定すると、ソルバがどう配置を最適化しても
   「基準を満たしたか」の判定は `gap_analysis` が担う。ソルバの最適化対象は
   「必要人員を満たす在勤の組合せ」に限られる。

4. **UI 側で基準だけ先に確認できる。**
   タブ 2（必要人員）で `Requirement.basis` を表示して確認し、そのあとタブ 3（シフト作成）を
   押す、という流れが成立するのは、必要人員の計算が最適化から独立しているからである。

5. **テストが速い。**
   配置基準の検証は MILP を起動せずに済む。

### 分断がもたらす制約

`solver` は「何人が必要か」を再計算できない。もし「在園児数から直接在勤数を決め直したい」という
要件が生じた場合、`solver` を触るのではなく `standards` の出力を差し替えることで対処する。

### `standard` 引数の位置づけ

`solve_shift` の `standard` 引数は `requirements` とは別の役割を持つ。これは配置基準そのものではなく、
**時間帯の性質（早朝保育 / 保育標準時間 / 延長保育）を判定するための基準**である。目的関数の
`early_shift_penalty` と `late_shift_penalty` をどの時間帯に掛けるか、また `gap_analysis` の
違反検査（`AVOID_EARLY_CONFLICT` など）で使う。省略時は全時間帯が `SlotKind.NORMAL` として
扱われる。

## 5. データフロー

### 全体像

```
[園児の登降園予定]
      |
      |  CSV / Excel / JSON
      v
  data_loader.read_bundle()
      |
      v
  LoadResult { children[], staff[], preferences{}, issues[] }
      |
      +--> 職員と希望休はそのまま solver へ渡す
      |
      v
  standards.build_requirements(children, days, standard, day_open, day_close, ...)
      |
      v
  RequirementTable { rows: {date: [Requirement, ...]}, slots: (Slot, ...) }
      |
      +--> (表示) tab_requirements: total_needed_hours / peak_requirement / basis
      |
      v
  solver.solve_shift(children, staff, requirements, preferences, weights,
                     fixed_assignments, settings, time_limit_sec, standard)
      |
      v
  SolveResult { status, shift_days[], assignments[], objective_value,
                violations[], messages[], stats{} }
      |
      +--> gap_analysis.analyze_gap(requirements, result, staff)     -> GapReport
      +--> gap_analysis.check_violations(requirements, result, ...)  -> Violation[]
      |
      v
  exporter.shift_to_dataframe / payroll_dataframe / requirements_dataframe /
            report.to_dataframe / to_ics / summary_markdown / export_bundle_zip
      |
      v
  shift.csv / payroll.csv / requirements.csv / gap.csv / violations.csv /
  shift.ics / summary.md / bundle.zip
```

### 5.1 1 日分の例

1. `ChildPlan` が 3 件（0 歳児 1 名、1 歳児 2 名）登録されている
2. `build_requirements` が `Slot` ごとに在園児数を数え、`headcount_for` で必要人員を求める
3. `_apply_min_two` が 2 名ルールで底上げする
4. `Requirement(day, slot, age_class, child_count, needed_staff, needed_qualified, slot_kind, basis, is_binding)` ができる
5. `solve_shift` が `RequirementTable` を受け取り、MILP を構築して CBC で解く
6. `decode_solution` が変数値から `ShiftDay`（職員と時間帯のマトリクス）を復元する
7. `analyze_gap` が `Requirement` と `ShiftDay` を突き合わせ、`SlotGap` を作る
8. `check_violations` が法令と契約と希望を検査し、`Violation` を作る
9. `exporter` が `SolveResult` と `GapReport` を CSV / Excel / ICS にする

## 6. `domain.py` が「凍結された契約」になっている意味

`src/shiftai/domain.py` の冒頭にはこう書いてある:

```python
"""shiftai の共通ドメインモデル（このファイルは全モジュールが依存する「契約」です）。

このファイルだけは各サブエージェントが変更しません。変更が必要な場合は
このファイルに型を追加する形で行い、他モジュール側をそれに合わせてください。
"""
```

### 「契約」であるとはどういうことか

`domain` の型は層をまたぐ関数のシグネチャに現れる。仮に `ChildPlan` のフィールドを 1 つ変更すると、
次のすべてが壊れる。

- `data_loader.load_children` が作る `ChildPlan` の値
- `standards.count_children_by_slot` が読む属性
- `sample_data.make_children` の生成結果
- `solver.solve_shift` の引数 `children` の型
- `exporter` が読む属性
- `ui` の各タブ
- `tests/` の該当テスト

つまり `domain` の型定義は、全モジュールの公開 API と同義である。

### 変更の手順

`domain` を変更する場合は、必ず次の順序をとる。

1. **まず型を追加する**（既存フィールドの削除と型変更をしない）
   たとえば `ChildPlan` に boolean フィールドを 1 つ足すなら、既存フィールドの後ろに
   `default` 付きで追加する。`ChildPlan` は `frozen=True` なのでインスタンスは不変になる。

2. **生成側を実装する**
   - `data_loader` に対応する列があれば、そこで読む
   - 列がなければ `default` が使われる
   - `sample_data` の生成関数で明示的に設定する

3. **消費側を 1 モジュールずつ更新する**
   - `standards`: 新しいフラグが計算に効くなら受入ロジックを追加する
   - `solver`: 最適化に反映するなら変数と制約を追加する
   - `gap_analysis`: 検査項目を追加するなら `VIOLATION_CODE_LABELS` にコードを追加する
   - `exporter`: 出力列を追加するなら DataFrame の `columns` に追加する

4. **テストを追加する**
   - `tests/test_domain.py` に型の制約（`__post_init__` のバリデーション）を追加する
   - 影響を受けるモジュールのテストを追加する

5. **既存フィールドを変更または削除する場合は破壊的変更として扱う**
   全モジュールの該当箇所を一度に見直してから行う。一部のモジュールだけ直すと、import は
   成功するものの実行時に `AttributeError` になる。

### `domain` に置かないもの

- **副作用のある処理**（ファイル I/O、ネットワーク、最適化）
- **モジュールレベルの `pandas` / `numpy` / `pulp` への依存**
  ただし `RequirementTable.to_long_dataframe()` と `ShiftDay.to_frame()` は `pandas` を
  関数内で遅延 import している。モジュールレベルには `pandas` がない。

## 7. 層を変更するときのチェックリスト

- [ ] 新しい層を追加する場合、`domain` を import する（`domain` 自体は他のモジュールを import しない）
- [ ] `domain` に型を追加する場合、`frozen=True` と `default` の要否を考える
- [ ] `solver` と `standards` の引数に、`RequirementTable` 以外の新しい入力形態を持ち込まない
- [ ] `gap_analysis` は `SolveResult` を計算し直さない（受け取った結果を読むだけにする）
- [ ] `exporter` は `domain` 以外のモジュールを import しない
- [ ] 遅延 import を使う前に、循環参照が本当に存在することを確認する
