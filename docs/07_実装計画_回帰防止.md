## T-01 週次判定が計画期間合計と比較する

### 現象

2週間以上の計画で、完全に適法なシフトに誤告が出る。**モデル側にも同じ構造的欠陥がある。**

```
週契約35h・週5出勤の2週間（完全適法）
  → WEEKLY_HOURS_EXCEEDED「56.00 時間で週44時間を超えています」×3   ← 週28h で合法
  → WEEKLY_DAYS_EXCEEDED「勤務日数が 14 日で契約上限（5 日）」×3    ← 週5日で合法
```

### 根本原因

4 箇所が独立に「期間全体」と「週単位の上限」を比較している。

| 箇所 | 現状 | 誤り |
| --- | --- | --- |
| `gap_analysis.py:649` | `total_hours > STATUTORY_WEEKLY_WORK_HOURS` | `total_hours` は期間合計（`:602`） |
| `gap_analysis.py:692` | `len(worked_days[sid] & set(days)) > c.max_weekly_days` | 期間内の全出勤日数 |
| `solver.py:687` | 全期間の `y` の総和が `max_weekly_days` 以下 | 2週間の計画で1人5日しか出勤できない |
| `solver.py:1398-1400` | `cap_days = min(workable, weekly_cap)` | 供給量推定も同じ誤り |

`check_violations` は `period_days`（`gap_analysis.py:386-409`）を受け取っているのに
この 4 箇所だけが参照しない。`MONTHLY_HOURS_EXCEEDED`（`:609`）は
`_contract_hours_band(c, period_days)` で正しく正規化されており、
**同じ関数内で判定基準が混在している**。

### 修正方針

1. `gap_analysis.py` に週窓ヘルパを追加する。計画開始日を起点に 7 日ずつ区切る。
   曜日起点に揃える必要はない。期間分割の起点に依存しない判定にすることが目的である。

   ```python
   def weekly_windows(days: Sequence[date], size: int = 7) -> list[list[date]]:
       """計画期間を size 日ごとの窓に分割する（末尾は短くなりうる）。"""
       ordered = sorted(days)
       return [ordered[i : i + size] for i in range(0, len(ordered), size)]
   ```

2. `WEEKLY_HOURS_EXCEEDED` を各窓の集計で判定し直す。**窓ごとに 1 件**の
   Violation とし、`detail` に窓の開始日を入れる。

3. `WEEKLY_DAYS_EXCEEDED` も同様。`max_weekly_days <= 0` のときはスキップする
   （`> 0` ガードは現行どおり維持）。

4. `solver._add_consecutive` の週出勤日数制約を**窓ごとの制約**に変更する。
   連続勤務のスライド窓（`:655-667`）と同じ分割粒度を使う。

5. `solver.supply_hours` の `cap_days` も窓単位に変更する。

6. 文言を更新する。
   - `gap_analysis.py:656` — 窓の日付を含む形にする
   - `VIOLATION_CODE_LABELS`（`gap_analysis.py:861`）— 「対象期間の勤務時間が週44時間を
     超えています」から「週の勤務が 44 時間を超えている週があります」へ

### 影響ファイル

### 回帰テスト

## T-02 `build_slots` が深夜閉所で例外を投げる

### 現象

```
build_slots(time(7,0), time(23,45), 30)
→ ValueError: Slot の end は start より後にしてください: Slot(start=23:30, end=0:0)
```

### 根本原因

`domain.py:187` の切り上げで `end` が 1440 になり、`to_time`（`domain.py:116`）の
`minutes %= 24*60` により `00:00` へ折り返す。`Slot.__post_init__`（`:128`）が
`end <= start` で拒否する。

影響は 23:45 閉所と30分粒度の組み合わせに限られる（2026-09-30 実測: 22:00 /
22:15 / 22:30 / 22:45 / 23:00 / 23:15 / 23:30 はすべて成功、23:45 のみ失敗）。
発生条件は `切り上げ後の end >= 1440`。UI のサイドバーは15分刻みの
`time_input` を提供しているため入力可能。

### 修正方針

**採用案: `time(0,0)` を終端側の「24:00」番兵として許可する。**

```python
# domain.py __post_init__
if self.end < self.start:
    raise ValueError(f"Slot の end は start より後にしてください: {self!r}")
if self.end == self.start and self.end != time(0, 0):
    raise ValueError(f"Slot の end は start より後にしてください: {self!r}")
```

`Slot` は `end > start` を要求するため、`end == time(0,0)` となりうるのは
**最後の時間帯だけ**（`start > 00:00`）であり曖昧さは生じない。

```python
@property
def end_minutes(self) -> int:
    """終端の分。終日（00:00 表記）は 1440 とする。"""
    minutes = to_minutes(self.end)
    return 1440 if (minutes == 0 and to_minutes(self.start) > 0) else minutes
```

`minutes` は `end_minutes - start_minutes` に委譲する。影響を受ける下流:
`solver._add_rest`（`slots[-1].end_minutes`）、`gap_analysis` の
`slots[prev[-1]].end_minutes`、`exporter.to_ics` の `to_minutes(last.end)`。

**不採用案**: 切り上げ結果を 1440 未満の最大粒度倍数に収まるよう `build_slots` で
クランプする。ただしこの場合 23:30〜23:45 の15分が**無人時間帯として黙って失われる**。
保育য়用人時間帯の欠落は重大リスクのため採用しない。

### 影響ファイル

`src/shiftai/domain.py`（+ `end_minutes` を利用する `solver.py` /
`gap_analysis.py` / `exporter.py` の各箇所を再確認）

### 回帰テスト

`tests/test_domain.py` に追記。

| ID | テスト | 検証内容 |
| --- | --- | --- |
| T-02-R1 | `test_build_slotsは24時閉所を許可する` | `build_slots(7:00, 23:45, 30)` が例外なく34区間を返す |
| T-02-R2 | `test_終端00時の区間長は正しい` | 最後の区間の `minutes == 15`、`.end_minutes == 1440` |
| T-02-R3 | `test_全時間帯の合計が開所から閉所まで一致する` | 区間の `minutes` 合計が 1005（7:00→23:45）、隙間・重複なし |

## T-03 `週最大出勤日数 = 0` が 5 に化ける

### 現象

```python
load_staff(csv)  # 週最大出勤日数=0
→ Contract(max_weekly_days=5, max_consecutive_days=5)
```

### 根本原因

`data_loader.py:757-758` の `_parse_int(view.get("週最大出勤日数"), 5) or 5`。
`_parse_int` は正しく `0` を返すため、`or` が偽とみなして 5 に落とす。
`0` を受け取った側の意味は明確で「**上限なし**」である。

- `solver.py:679` — `if st.contract.max_weekly_days > 0:`
- `solver.py:1651` — `>= contract.max_weekly_days > 0`
- `solver.py:1398-1399` — コメントに「0 のときは『上限なし』と解釈する」と明記
- `gap_analysis.py:692` — `> c.max_weekly_days > 0`

つまり**読み込み層だけがこの意味を打ち消している**。

### 修正方針

`None` を番兵として「列が無い・空」と「0 が明示された」を区別する。

```python
max_weekly_days = (_parse_int(view.get("週最大出勤日数"), None),)
# ...
resolved = member_max_weekly_days if member_max_weekly_days is not None else 5
```

`Contract.__post_init__`（`domain.py:279-283`）で `max_weekly_days >= 0` を
検証し、負値は読み込み時に `LoadIssue("error")` として記録して行を落とす。

### 影響ファイル

`src/shiftai/data_loader.py` / `src/shiftai/domain.py` / `docs/04_データ仕様.md`

## T-04 「配置対象外」職員が配置基準を充填する

### 現象

園長1名だけの構成で、保育基準（2名/時間帯）を完全に充足してしまう。

```

園長 E1 の勤務セル: 12/12 個
```

### 根本原因

`Role.ENJOGAKUIN = "園長・主任（配置対象外）"`（`domain.py:66`）と定義され、
`data_loader` に別名処理（`園長` / `主任` / `enjugakuin`）もあるが、

`sample_data.py:343` は「園長は配置基準の人数に計上しない前提で」とコメント

1. `domain.StaffMember` に配置可否プロパティを追加する。

   ```python
   @property
   def is_placeable(self) -> bool:

       return Role.ENJOGAKUIN not in self.roles
   ```

3. `solver.supply_hours`（`:1386`）と `_shortfall_supply`（`:1401`）でも除外する。
   **供給の過大評価も防げる。**

4. `gap_analysis.analyze_gap`（`:245`）と `check_violations`（`:459`）の配置人数集計でも
   除外する。`lookup` が不在を返すので実害は薄いが、統一する。

5. `exporter` は除外しない。行は表示し、内容が不在として出る。

6. 配置対象が 0 名になった場合のメッセージを `_build_cells` で事前に出す。
   現状は `_add_coverage`（`:492`）の「配置できる職員がいません」だけが頼りだが、

## T-05 `summarize()` が人件費単価を無視する

### 現象

```
人件費単価 1500 → summarize["人件費"] =  9,000
人件費単価 3000 → summarize["人件費"] =  9,000   ← 変わらない
正しい値                                  = 18,000
```

### 根本原因

`gap_analysis.py:957` が `compute_cost(result, staff)` と呼び `settings` を渡さない。
`compute_cost`（`:912-932`）は `settings or FacilitySettings()` で 1500.0 に固定される。
`tab_solve.py` の表示カードは `settings` 付きで直接呼ぶため正しい。
**同じ画面内で2つの値が出る。**

さらに**「人件費」の定義が2つある**。

| 関数 | 定義 | 休憩の扱い |
| --- | --- | --- |
| `compute_cost` | 在勤時間（勤務と休憩の合計） | 有給 |
| `exporter.payroll_dataframe` | 実働時間（勤務 − 休憩） | 無給 |

`summary_markdown` は `payroll` の合計を使い、`tab_solve` の表示カードは
`compute_cost` を使う。UI と `summary.md` で人件費が食い違う。

### 修正方針

1. `summarize()` に `settings` 引数を追加する。


## 4.1 マーカーの規約

## 計画から変更した点

計画作成時に分からなかったことが実装中に判明し、方針を変えた箇所。

### 1. T-01: 検査は「非重複の週区画」にした

計画では報告も重複窓（sliding）にすると書いていたが、2週間の計画で
**1人あたり同じ週の違反が 8 件並列してに出る**ため使えない。
判定の正しさは重複窓で担保しつつ、報告は `weekly_periods`（重複しない週区画）にした。

### 2. T-01: 供給量は非重複窓が必須

当初重複窓で合算したところ、14日計画の供給量が **1050 人時**（物理的上限 420 人時）
という非現実的な値になった。重複窓は同じ日を数えてしまうため、`supply_hours` だけは
`weekly_periods` を使うことにした。この値は回帰テスト `test_供給人時は物理的上限を超えない`
で固定している。

### 3. T-01-R7: 計画の前提が成立していなかった

計画は「モデルは週ごとに週最大出勤日数を守る」を期待していたが、週上限は
**soft 制約**（罚変数 + 罚金）であり、配置基準とのトレードオフで
意図的に破られる。必要人員に対する供給が不足する構成では 5日/週 では
物理的に満たせないため、モデルが正しく違反を許容する。
よって R7 を「14日計画で 1 人が 5 日を超えて出勤できること」
（修正前は**計画期間全体**に対して `Σy <= 5` が課されていたため不可能だったこと）
に変更した。これは元の欠陥を確実に検出する条件である。

### 4. T-05: 給与 CSV にも二重控除があった

計画は人件費の「基準の相違」だけを指摘していたが、
`payroll_dataframe` は `worked_min`（休憩を含まない値）からさらに `break_min` を
引いており、**休憩時間が二重控除されていた**。実働基準への統一に伴って修正した。

### 5. T-04: 除外の位置は「入口で1回」が正しく、貪欲法にも必要だった

計画は `_build_cells` での除外を提案していたが、そこで除外すると
`_add_hours_objective` が `ctx.hours[sid]` を参照して `KeyError` となり、
貪欲法へフォールバックして**そこで園長が配置される**という副作用が出た。
入口の `_build_problem` で一度だけ除外する形に変更した。

### 6. T-06: 手動マーカーではなく自動付与とした

計画はフィクスチャ集約を推奨していたが、テストが `solve_shift` を
直接呼ぶケースが多く hyped 少なかった。`conftest.py` の
`pytest_collection_modifyitems` で AST から CBC 呼び出しを検出して自動付与する方式にした。
適用後は **98件**（手動付与時は 6件）が `slow` になった。

### 7. T-08: 終了コードの結合テストは成立しない

サンプルは必ず BLOCKER が出るため、`--strict` で 3 を返す経路を結合テストでは作れない。
判定を `resolve_exit_code` に切り出し、合成した違反一覧で判定表を網羅的に検証した
（実装修正のない最小リファクタ）。

### 8. T-13: 「週44時間」の記述は 10箇所教学中

`config` のコメント、`sidebar`、`tab_solve`、`tab_shift`、`domain`、`solver`、
`gap_analysis` のラベル、`README`、`docs/02` を更新した。

### 9. T-12: 計画で把握していた 5件 に加え 6件 見つかった

検査テストを実装してから実際に全ファイルを走査した時点で、追加で 6件 の混入が見つかった。
**韓国語 5件**（日本語の文中に、2文字または3文字のハングル音が「延長」「ために」「別に」「違反」の位置に混入していた）と
README の 1件。検査は韓国語（ハングル）も検出するように拡張している。

## 追加で発覚した既存の問題

### 貪欲法の実スケールで出力が再現しない（T-08 の副産物）

同じ入力・同じ `--seed` で `shift.csv` の内容が変わることをテストが検出した。
原因は**時間制限に間に合わず「実行可能解」で終わる場合、CBC の探索が経過時間に
左右される**ことである。最適解が求まる規模なら完全に一致する。
`test_seedで同じ入力なら同じ出力になる` は最適解が求まる規模の入力に限定し、
この制約を docstring に明記した。運用上の注意書きとして共有すべきである。

### 貪欲法のカバレッジ閾値が不正確だった（T-04 の副産物）

`test_大規模貪欲法のカバレッジは80分以上` は **園長を誤って配置していた挙動**を
基準に較正されていた。園長を除外する修正後、28名中1名が配置可能から外れ
カバレッジは 0.8118 → 0.7921 に下がった。閾値を 0.78 に下げ、
その経緯を docstring に記録した。壊れた品質 0.371 を検出できる水準は維持している。
