# 11. 実装計画 — 労働基準法の判定と休憩制約

レビュー（2026-10-03 時点）で確認された法令解釈・ソルバ構造の問題を、
**1 コミット = 1 ステップ** に分解した実装計画。

各ステップは「1 ファイル・1 挙動」を原則とし、
**どのステップも途中までコミットしても CLI 終了コードを壊さない**ように順序を設計している。

---

## 0. 法的前提の訂正（実装前に必ず共有すること）

本計画の前提組織に **3 件の誤り**が含まれる。実装前に正す。

### 0.1 「週44時間は従業員10人未満の保育所などの特例」ではない

| 前提（指摘内容） | 実態 |
| --- | --- |
| 週44時間は「従業員10人未満の保育所などに認められる特例の上限」 | **誤り**。週44時間は **2019-04-01 に失効した旧来の一般法定週労働時間**（第32条の4 旧）に由来する。認可保育所にも無条件に適用されていた |

現行の枠組み（混ざりなく書き分ける）:

| 枠組み | 条文 | 内容 |
| --- | --- | --- |
| **基本労働時間** | 第32条第1項 | 1日 8 時間・1週 40 時間。これを超える分は原則「時間外労働」 |
| **法定上限時間** | 第32条の4 | 時間外労働が累積できる上限。月 45 時間・年 360 時間（第36条の協定が必要）。**2024-04-01 の改正で従業者数規模別に据置き／引き下げが分かれている** |
| **36協定（特殊）** | 第36条 | 上記を超える労働を協定で定め、割増賃金を支払う制度。本ツールの `overtime_allowed` はこれに対応する |

したがって本ツールが持つ `STATUTORY_WEEKLY_WORK_HOURS = 44` は
**「社内目安（旧基準・厳しい方）」**という位置づけであり、法的根拠を主張してはならない。

> **要確認（人手では判定できない）**: 2024 年改正後の正確な法定上限時間は
> **従業者数（30人未満／以上）によって異なる**ため、本ツールは数値を断定しない。
> `docs/03_配置基準と自治体ルール.md` の未対応リストに「法定上限時間の従業者数別
> 値は園ごとの確認事項」を追記し、UI では法定値を断定しない（LB-03 / LB-06）。

### 0.2 「1日10時間の上限（労基法32条・5条）」という条文は存在するが、要件を満たすか不明のため園ルールとして扱う

- `config.py:37-41` のコメント「労働基準法第32条・第34条の1日法定労働時間の上限（10時間）」は
  **条文としては存在しない**（実際は第32条の5が1日10時間の上限を定めるが、著しい繁閑差・常時使用労働者数要件・協定・前日通知などの要件を満たすかは本ツールでは判定不能）。
- 10 時間を**社内ルールとして使うこと自体は構わない**が、
  「法定」「条文」と書くと法令の引用として流通してしまう。
  → LB-01 / LB-03 で「**園ルール（実働 10 時間を上限）**」と書き換える。

### 0.3 「法定8時間 + 休憩45分 = 8.75時間」という比較そのものが誤り

- `config.py:46-49` `STATUTORY_DAILY_LIMIT_HOURS = 8.75` は
  `gap_analysis.py:502` で **`work_minutes`（休憩を含まない実働分数）**と比較されている。
  実働 9 時間が「休憩込み 8.75 時間」，于是超過と判定される。
- **法定労働時間は実働 8 時間**である（第32条第1項）。
- 休憩 45 分／60 分は第9条の**別個別の要件**であり、8 時間に足し込むものではない。
  → `STATUTORY_DAILY_LIMIT_HOURS` を判定から外す（LB-10 / FD-01）。

### 0.4 本計画で守る原則

| 原則 | 理由 |
| --- | --- |
| コードは**社内目安**を `STATUTORY_*` で名付けない | 内部目安を法令として流通させない（既存 T-13 の方針を継承） |
| 機械で判定できないものは**断定しない** | `compliance.py` の `UNKNOWN` 方針と一致 |
| 1 ステップ = 1 コミット | 途中で `git revert` しても他機能を壊さない |
| **どのステップでも終了コードが不変** | サンプルデータが BLOCKER を含んでも開発途中の混乱を防ぐ |

### 1.3 .Rest と期待：休憩をハード制約にした場合の配置影響（見積り）

- 勤務セルのうち休憩に変換すべきは、0分 7 件 × 2 時間帯 + 30分 28 件 × 1 時間帯
  = **最大 42 セル分のカバレッジ損失**（30分粒度換算）。
- 配置可能セル総数は 26 名 × 25 時間帯 × 7 日 ≒ 4,550。
  損失率 **0.9 %**。コバレッジとの取り合いは**十分回避可能**と推定される。
- ただし 30 分以下の「短い勤務」職員（0.5h / 1.0h / 1.5h の 20 職員・日）は
  **法定上休憩が不要**。現状の `_add_breaks` は在这些日程にも一律 60 分を要求している（§2.2）。
  勤務時間が閾値未満なら要求しないよう直すことが、本計画の中心である。

## 2. 現状の構造的問題

### 2.1 休憩不足（`BREAK_INSUFFICIENT`）— 検査は正しい、深刻度だけが誤り

`gap_analysis.py:567-584` の `_required_break_minutes(work_minutes)`
（`gap_analysis.py:359-367`）は **勤務時間に比例して正しく判定している**。
誤っているのは次の 2 点だけ。

| 問題 | 位置 | 実害 |
| --- | --- | --- |
| 深刻度が WARNING | `gap_analysis.py:575` | 労基法第9条の義務違反が「要調整」扱いで配布されうる |
| メッセージの基準分数 | `gap_analysis.py:578` | `（基準 {STATUTORY_BREAK_MINUTES} 分）` が**45 分固定**。`required` が 60 分（園基準）のとき「基準45分必要」と誤表示 |

36協定があっても**免除できない**義務であるため BLOCKER が正しい。

### 2.2 `_add_breaks` が「勤務時間に無関係」に全勤務日に 60 分を要求する

`solver.py:653-684`：

```python
need_slots = min(max(1, -(-break_minutes // gran)), max(0, cap_min // gran))
...
ctx.prob += _linear(items) >= need_slots * yvar - deficit
```

- `need_slots` は **`break_minutes`（園基準 60 分）と粒度だけ**から決まり、
  **その日の勤務分には一切依存しない**。
- したがって 1.5 時間の勤務にも 2 時間帯（＝60 分）の休憩が要求される。
- soft（`deficit` に `break_conflict_penalty = 50.0`）なので、
  **配置カバレッジ（`shortfall_penalty = 1000.0` ではないが `overstaff_penalty = 1.0`）と
  競合した結果、0 分・30 分の解が選ばれる**。
- しかも `_add_workload`（`solver.py:640-650`）が同時休憩超過にも
  **同じ重み `break_conflict_penalty = 50.0`** を掛けるため、
  休憩を置くと二重に罰せられる。

### 2.3 1 日の時間超過の基準が誤り

| 問題 | 位置 | 実害 |
| --- | --- | --- |
| 8.75h（実働）と比較 | `gap_analysis.py:502-516` | 9.0〜10.0 時間の **完全合法な** 勤務に `STATUTORY_DAILY_HOURS` が出る |
| 残業不可でも 10h まで許す | `solver.py:104-109` / `live_validation.py:429-435` | `overtime_allowed=False` の職員が法定 8 時間を超えてもモデルが受け入れる |
| 「法定上限を超えて」の表示 | `gap_analysis.py:508-510` / `VIOLATION_CODE_LABELS:896` | 36協定＋割増賃金が揃っていれば合法なのに「法定上限超過」と表示される |

### 2.4 分割勤務

- `gap_analysis.py:599-613` は 3 ブロック以上で `SPLIT_SHIFT`（WARNING）。
- `solver._add_block`（`solver.py:480-481`）が duty / brk とも `obj` を渡して**ソフト化**しているため、
  サンプルでは **80 件の分割勤務**が発生している。
- 合法性違反ではないため**判定の深刻度は WARNING のまま**とする（本計画でも変更しない）。
  ただし現場基準として「勤務は最大 2 ブロック（勤務・休憩・勤務）」を
  モデル側で強制する（フェーズ 3）。

### FE-03 `_add_breaks` を「勤務時間連動のハード制約」に書き換える

**変更ファイル**: `src/shiftai/solver.py`（`_add_breaks` を全面書き換え）

**現在の形（`solver.py:653-684`）**

```python

...

```

**新しい形**

`_add_breaks` のシグネチャを次の形に変更し、`hard` で挙動を切り替える。

```python
def _add_breaks(
    ctx, staff, requirements, *,
    gran: int, facility_break_minutes: int, stat_break_minutes: int,
    hard: bool, obj: list | None = None, weights: "ObjectiveWeights | None" = None,
) -> None:
    # 勤務時間に比例した最低休憩を課す。
    # hard=True は罰変数を持たないハード制約、False は従来の brkdef 罰変数。
    ...
```

**定式化**

職員・日の組ごとに 0/1 変数 `f6`（実働が 6 時間を超える）と
`f8`（実働が 8 時間を超える）を 1 個ずつ置く。
`brk` はその日の休憩変数の合計、`work` は `ctx.day_work`（実働分数の線形式）、
`cap` は 1 日上限（分）、`gran` は時間帯の最小分数である。

```
(1)  brk >= need6 * f6 + (need8 - need6) * f8
(2)  f8 <= f6
(3)  work <= T6 + (cap - T6) * f6        (4) work >= (T6 + gran) * f6
(5)  work <= T8 + (cap - T8) * f8        (6) work >= (T8 + gran) * f8
```

| 記号 | 値 |
| --- | --- |
| `T6` / `T8` | `6 * 60` / `8 * 60`（法定の閾値。分） |
| `need6` | `ceil(max(stat_break_minutes, facility_break_minutes) / gran)` |
| `need8` | `ceil(60 / gran)`（法定の 8 時間超要件） |

(3)(4) は「`f6 = 1` ⟺ 実働が `T6` を超える」、(5)(6) は「`f8 = 1` ⟺ 実働が `T8` を超える」
という**指示変数の定義**である。下限を `T6 + gran` でよいのは（`T6 + 1` でなくてよいのは）、
1 日の勤務分数が時間帯長の倍数になる_ため_である（境界の正確さは FE-03-R8 で固定する）。

| ケース | `f6` | `f8` | 必要な休憩 |
| --- | :---: | :---: | --- |
| 勤務 5.5h | 0 | 0 | **0**（従来は一律 60 分を要求していた＝主要な削減） |
| 勤務 6.5h | 1 | 0 | `need6` = 2 時間帯（60 分） |
| 勤務 9.0h | 1 | 1 | `need8` = 2 時間帯（60 分） |
| 勤務 10.0h | 1 | 1 | 60 分 |

`hard=False` の場合は (1) の左辺に罰変数を差し込み、
`obj` に `break_conflict_penalty * brkdef` を加える（= 現行の挙動）。

**重要**: `ctx.day_work[(sid, day)]` は **勤務分数の線形式**であり、
`_build_cells`（`solver.py:490`）で必ず設定されている。
定数になっている日（休園日・全セル確定）は `isinstance(work, (int, float))` で除外する。

## 10. フェーズ 6 — 勤務パターン方式（案C）の RFC

**このフェーズは実装しない。** フェーズ 0〜5 の完了後に設計判断をするための
**調査・設計ドキュメント**を作る。対象は 1 ファイル（`docs/12_...`）。

### 10.1 解決する問題

| 現状の限界 | フェーズ 0〜5 後の改善 |
| --- | --- |
| 分割勤務 80 件・分断休憩 55 件 | **構造的に 0 件**（FB-01 / FB-02） |
| 60 秒で最適解に届かない（FEASIBLE 終了） | 変数数が 1/100 になり**最適解に到達**.Execute |

### 10.2 案C の定式化（案）

`w` / `b` のセル変数を廃止し、**勤務パターンの選択変数だけ**を置く。

```
変数: x[staff, day, pattern] ∈ {0,1}      （_pattern は (枠, 休憩位置) の組）
制約: Σ_pattern x[staff, day, pattern] == y[staff, day]      1日に1枠だけ
      Σ_{p: 時間帯 i を含む} x[staff, day, p] >= need[i]     配置基準（hard）
      Σ_p x[staff, day, p] * work_minutes(p) <= daily_cap
      ...
```

- `w[s,d,i]` は `Σ_{p: i ∈ work(p)} x[s,d,p]` として**導出**される。
  PuLP 側で展開すれば `ctx.work` の出力形式をそのまま維持できる。
- パターン定義は `shiftai.shift_patterns.ShiftPattern` に
  **`break_offset` を追加**（何時間帯目から休憩を取るか）。
  現在の `ShiftPattern` は `(key, label, start, end)` のみで休憩位置を持たない。

### 10.3 満たすべき前提条件（実装前に満たす必要がある）

| ID | 前提条件 | 検証方法 |
| --- | --- | --- |
| RP-01 | **全時間帯がパターンで被覆される** | 精算表の和集合が `slots` の全時間帯を含むこと |
| RP-02 | **必要人員がパターン上限を超えない** | 任意の時間帯について `Σ_p min(1, ...) >= need[i]` |
| RP-03 | **契約時間帯がパターン内** | 各職員の `earliest_start`/`latest_end` がパターンをまたぐ場合の扱い |
| RP-04 | **手動確定セル**がパターンと整合 | 手動固定が 2 パターンをまたぐ場合の扱い |
| RP-05 | **休憩の閾値判定**（6h/8h）がパターン上で可能 | パターン長と休憩量が法定を満たす組み合わせのみを残す |

RP-02 が満たらない園（必要人員がパターン数より多い）では**そもそも解が存在しない**。
この判定は `solver.shortfall_rows`（既存）を拡張してCBC を起動せずに判定できる。

### 10.4 移行戦略

```
--assignment-mode cells     （既定・現行。フェーズ 0〜5 の実装）
--assignment-mode patterns  （新方式。案件ごとに切替）
```

- 両モードの**結果を同じ検査関数**（`gap_analysis.check_violations`）で評価し、
  UI 上でも **BLOCKER 件数の比較**ができるようにする。
- `patterns` モードが全ケースで BLOCKER 0 を達成してから既定へ切り替える。

| 効果 | 期待 |
| --- | --- |
| 分割勤務・分断休憩 | 構造的に発生しない |
