# 14. 実装計画 — 違反激増の根本改善（罰則序列・区間列挙・検査統合）

本計画は、自動シフト作成時に **法令違反（BLOCKER）と要調整（WARNING）が異常に多い**問題を、
原因①②③（後述）ごとに根本から修正し、かつリグレッションを防ぐための詳細実装計画である。

対象リポジトリ: `E:\nushift\nushift`（本ファイル: `docs/14_実装計画_違反激増の根本改善.md`）

**低性能な LLM が実装する前提**で、各ステップは「1 ステップ = 1 コミット = 10〜30 分の作業」に分解している。
各ステップには「変更ファイル」「作業内容（具体的な編集指示）」「テスト・実行コマンド」「完了条件」を必ず明記した。
**ステップを飛ばしたり、順番を入れ替えたりしないこと。** 各ステップは前ステップの成果物（特にベースライン JSON）に依存する。

## 0. 背景：何が起きているか（証拠）

`.venv\Scripts\python.exe -m shiftai solve --sample --time-limit 60`（デフォルト = 厳格モード L0）の実測:

- 配置基準の不足セル **0 件**（充足率 100%）
- 法令違反（BLOCKER）**17 件** ／ 要調整 **164 件**（目的関数値 315,842）

| コード | 件数 | 実態 |
|---|---|---|
| SPLIT_SHIFT | 79 | 1日3〜8ブロックに勤務が分断 |
| BREAK_FRAGMENTED | 52 | 休憩が2〜7個に分断 |
| OVERTIME_REQUIRES_36AGREEMENT | 23 | 9〜10時間勤務の日が量産 |
| BREAK_INSUFFICIENT | 17 | 休憩0〜30分（労基法34条違反＝BLOCKER） |
| MONTHLY_HOURS_EXCEEDED / SHORT | 8 | 週契約±15%バンドの境界判定 |

過去出力 `out/summary.md` でも同傾向（BLOCKER 20／要調整 142）。

### 原因① 法令義務が「罰金で買える」設計

- `domain.py` の `ObjectiveWeights`: `shortfall_penalty=1000` ＞ `break_deficit_penalty=600` ＞ `split_duty_penalty=300` ＞ `break_edge_penalty=800`(相対)
  - `break_deficit_penalty` の docstring は「配置基準を満たす代わりに休憩を削ることが起きないように他のどの目的項より大きい値にしている」と謳うが、実測では `shortfall_penalty`(1000) に**負けている**。つまり **「1 人足りない（不足 1000）より休憩を削る（600）方が安い」** ので、ソルバは法令違反を合理的に選ぶ。
- `solver.py` の `_MAX_INTERVAL_CANDIDATES = 100`: 在勤1ブロック・休憩1ブロックのハード制約は区間列挙（候補 O(n²)）で張る。30分粒度×12時間の日（25時間帯）では候補が **約300** となり必ず上限超え → **ソフトペナルティ（300/ブロック）へサイレントフォールバック**（`solver.py:118`, `solver.py:573`, `_add_duty_block` 内の `_add_interval_block` 分岐）。標準的な営業時間ではハード制約が普段から機能していない。

### 原因② ソルバと検査器（`gap_analysis`）が別々の基準で判定している

- 休憩: ソルバ=ソフト(600)、検査器=法定 BLOCKER（`gap_analysis.py` `check_violations` の `BREAK_INSUFFICIENT`）
- 残業: ソルバ=10h まで許容（`config.STATUTORY_MAX_DAILY_WORK_HOURS`）、検査器=8h 超を1日ごとに WARNING
- 月間: ソルバ=`month_fraction` 換算の min/max_monthly、検査器=週契約×日数/7±15% の独自バンド（`_contract_hours_band`）
  - 6日計画・週40h 契約の正職員（5日×8h＝40h）でも「上限39.4h 超え」として要調整扱いになる
- 週44時間: ソルバは**計画全体の合計**と比較する既知バグ R2-SOL-02（`solver.py` の `_add_hours_objective` 内 `NOTE(R2-SOL-02)` コメント、修正延期のまま）、検査器は週窓で判定
- 件数の膨張: `OUTSIDE_CONTRACT_HOURS` / `WORK_ON_UNAVAILABLE` / `WORK_ON_CLOSED_DAY` は**時間帯ごとに別行**で出力される。集約がない

### 原因③ フォールバックと事前ゲートの弱さ

- 1パス目（配置基準ハード）解なし → 2パス目（配置基準を罰変数化）→ 貪欲法、と落ちていき、各段階で法令・運用違反を含む解が「実行可能解」として出てくる
- 求解前の実現可能性チェック（`solver.shortfall_rows` / `supply_hours`）は UI の参考情報に留まり、**需要>供給でも求解が止まらない**
- 弛緩モード L3 では休憩・休息ペナルティを完全に無効化するため BLOCKER がさらに増える

## 1. 改善方針（3案）と本計画での対応

| 案 | 内容 | 本計画のフェーズ |
|---|---|---|
| 案1 | ①法定義務を罰金で買えないように重み序列を修正、②区間列挙の実用化 | Phase D（序列修正）, Phase E（区間列挙） |
| 案2 | 法定閾値・計算式の単一ソース化（`statutory_rules.py`）＋検査器の整合 | Phase B（単一ソース化）, Phase C（検査器整合）, Phase F（週44修正） |
| 案3 | 違反の集約表示＋求解前ゲート（需要>供給なら求解を止める） | Phase A（集約）, Phase G（ゲート） |

### 設計上の決定事項（勝手に変えないこと）

1. **不足（SHORTFALL）は BLOCKER のまま**。配置基準（児童福祉法上の安全）を緩めない方針は維持する。違法シフトを出すより「不足」を出すほうが誠実である。
2. **法定休憩（労基法34条）は最重要**。`break_deficit_penalty` を `shortfall_penalty` より十分大きくする（6000）。
3. **週44時間は「社内目安」のまま**（法定ではない）。修正するのはソルバ側の計算範囲（R2-SOL-02）のみで、閾値 44h 自体は変えない。
4. **`VARIABLE_HOURS_ADAPTED`（適法な週を報告する INFO）は出力から除去**（違反一覧を濁さない）。
5. 36協定ありで8h超の勤務は WARNING ではなく **INFO**（確認事項）へ格下げ。
6. `solver_core/` はアプリから未参照の並行実装（`solver.py` が正）。**本計画では一切触らない。**
7. 集約は「表示件数」を減らすだけで、**警告メッセージの存在自体は消さない**（`SPLIT_SHIFT` の意味が失われないように）。

- Python 3.12+、`from __future__ import annotations` を各モジュール先頭に置く。

- `pytest` が failing になったら、まず `.venv\Scripts\python.exe -m pytest -q --tb=short` で最初の失敗を読む。症状別の対処:
  - `AssertionError` で violation 件数差 → そのステップの「ベースライン/ゴールデン再生成」手順を実行（意図した変更なら再生成が正解）。**無断でアサーションを緩めないこと。**
  - `ImportError` / `NameError` → 編集ミス。ステップの指示と差分を見直す。
  - Solver が `INFEASIBLE` に悪化した → Phase E の計測ステップ（Step 31→32）へ。**`MAX_INTERVAL_CANDIDATES` を上げすぎてはいけない。**

### Step 2: `aggregate_violations()` 純関数の追加（Phase A）

- **目的**: 違反リストを `(code, staff_id, day)` で集約する関数を、まだ呼び出さずに作る。
- **変更ファイル**: `src/shiftai/gap_analysis.py`
- **作業内容**:

  2. モジュール末尾（`_minutes` 関数の前など分かりやすい場所）に以下を追加:
     ```python
     def aggregate_violations(violations):
         """(code, staff_id, day) が同じ違反を 1 件に集約して返す。

         時間帯ごとに 1 行ずつ出ていた違反を「1 人・1 日・1 コード = 1 行」にまとめる。
         集約時は `detail["slots"]` に対象時間帯ラベル、`detail["count"]` に件数を入れる。
         深刻度・日付ソート順（既存の sort キー）は維持する。
         """
         order: list[tuple] = []
         groups: dict[tuple, list] = {}
         for v in violations:
             key = (v.code, v.staff_id, v.day)
             if key not in groups:
                 order.append(key)
                 groups[key] = []
             groups[key].append(v)
         out = []
         for key in order:
             items = groups[key]
             if len(items) == 1:
                 out.append(items[0])
                 continue
             first = items[0]
             slots = [ (getattr(i.slot, "label", None)) for i in items ]
             slots = [s for s in slots if s]
             merged_detail = dict(first.detail or {})
             merged_detail["count"] = len(items)
             if slots:
                 merged_detail["slots"] = slots
             merged_message = first.message + f"（他 {len(items) - 1} 箇所）" if slots else first.message
             out.append(Violation(
                 severity=first.severity, code=first.code,
                 message=merged_message, day=first.day, slot=None,
                 staff_id=first.staff_id, detail=merged_detail,
             ))
         return out
     ```

  4. **まだ `check_violations` から呼ばない。**
- **テスト**: このステップではテストを書かない（次の Step 3）。`ruff check .` のみ。
- **完了条件**: import エラーがなく `python -c "from shiftai.gap_analysis import aggregate_violations"` が成功。

  値を変えたいときはこのモジュールと tests/test_statutory_rules.py だけを直す。
  """
  STATUTORY_DAILY_WORK_HOURS = 8
  STATUTORY_MAX_DAILY_WORK_HOURS = 10.0
  STATUTORY_OVERTIME_MULTIPLIER = 1.25
  INTERNAL_DAILY_LONG_HOURS = STATUTORY_DAILY_WORK_HOURS + 1.0
  STATUTORY_WEEKLY_WORK_HOURS = 44  # 社内目安（法定ではない）

  DEFAULT_BREAK_MINUTES = 60
  BAND_TOLERANCE_HOURS = 0.25  # 月間バンド判定の許容差（0.1h 超過で違反にしない）

  def required_break_minutes(work_minutes: int) -> int:

      need = 0
      for threshold, minutes in STATUTORY_BREAK_THRESHOLDS:
          if work_minutes > threshold:

  def daily_cap_minutes(contract) -> int:

## 6. リスクとロールバック

| リスク | 症状 | 対処 |
|---|---|---|
| 重み変更（Phase D）で配置不足が発生 | `violation_baseline.json` に `SHORTFALL_*` が新規出現 | これは**意図した挙動**（違法を黙って出さず不足を可視化する方針）。不足が出る場合は samples の時点で職員数・園児数・開所時間の見直しが必要とドキュメント（Step 41）に明記。テストを無理に green にしない。 |
| 区間列挙の固定長化（Phase E）で解が悪化 | pass1 解なし・所要時間増大 | `MAX_INTERVAL_CANDIDATES` を引き上げすぎない（150 を超えない）。所要時間が 2 倍超なら 100 に戻す（Step 33 の手順）。 |
| 集約（Phase A）でテストが多数失敗 | 件数期待の大量更新 | Step 4 の「件数期待だけを更新・意味を変えない」を徹底。緩めない・削除しない。 |
| 月間バンド正規化（Step 14/15）で月次報告の目安が弱まる | 「月間の参考警告」が出にくくなる | これは意図した変更（短期計画では意味をなさないため）。月単位（30日）の計画では従来どおり判定される。 |
| 週44 修正（Step 35）で目的関数が変動 | golden master の objective_value が動く | Step 35/36 適用後に golden master 再生成（§5.1）。status/work_count が妥当であることだけ確認。 |
| `statutory_rules.py` の定数が既存の挙動と微妙にズレる | 休憩・上限テストの失敗 | Step 9 で式を「完全一致」に保っていることを確認。ズレが出たら即 `git restore` し、既存 `config.py`/`domain.py` の式と並べて差分を取る。 |

- **共通のロールバック**: 各ステップ = 1 コミットなので、壊れたら `git restore --staged --worktree <ファイル>` または `git revert <コミット>`。複数ファイルにまたがる場合はステップ単位で巻き戻す。
- **変更の追跡**: 各フェーズ完了時に `git log --oneline` で 1 行ずつ確認し、順序が壊れていないことを確認する。
