## 0. 背景

第2・3段階（求解性能）の全36ステップ実装完了後、review-loop 第1ラウンドのコードレビュー
（`a5d785a..HEAD`、29コミット）を実施した。判定は `REVIEWLOOP-VERDICT-CHANGES`
（重大3件・中程度6件・軽微5件、合計14指摘）。

指摘の中心は、**週次 hierarchical エンジンの既定パスが実質壊れている**ことである。
`weekly.py` が `monthly_holiday_target=8` を 7 日のホライズンに渡しており、
Stage 1 制約3が `勤務上限 = 7 - 8 = -1` の必違約となる。Stage 1 はソルバーの
status を無視して varValue を読むため、実行不可能時は全員 OFF を返し、
Stage 2 で全スロット OFF 固定に潰れる。

実証結果（7日×28名、`_solve_stage1_daily_patterns` 単独実行）:

```
Stage1 割当: total=196 OFF=196 非OFF=0
```

つまり従来の KPI「達成」判定（K2 wall 5.2秒 / K4 gap 0.0%）は
**全員OFF模型が瞬殺で解けた**ことによる見かけ上の達成であり、修正後の再測定が必要である。

## 2. 重大指摘の詳細実装手順

### 指摘1: 公休目標の期間比例補正（monthly.py）

`Contract` 実属性（domain.py:375）: `max_weekly_days: int = 5` のみ。
`monthly_holiday_target` / `weekly_work_days` は**存在しない**（既存の hasattr 分岐は死んだコード）。

モジュールレベルにヘルパーを追加し、制約3・制約6の両方で使用する:

```python
def _target_holidays(monthly_target: int, days_count: int, contract: Contract | None) -> int:
    # 30 日基準の公休目標を期間に比例補正（30 日では元の値そのまま）
    target = round(monthly_target * days_count / 30.0)
    # 勤務日数上限が 0/負にならないよう保証
    target = min(target, max(0, days_count - 1))
    max_wd = getattr(contract, "max_weekly_days", None) if contract else None
    if max_wd:
        est_work_days = round(max_wd * days_count / 7.0)
        target = max(target, max(0, days_count - est_work_days))
    return max(0, target)
```

期待値（`monthly_holiday_target=8`、契約 `max_weekly_days=5`）:

| ホライズン | 比例補正 | 契約導出 | 採用 | 勤務上限 | 備考 |
|-----------|---------|---------|------|---------|------|
| 30日（月次） | 8 | 9 | 9 | 21日 | 旧 22日から厳格化（週平均5日の整合） |
| 7日（週次） | 2 | 2 | 2 | 5日 | **旧 -1 で必違約→全員OFF の修復点** |
| 14日 | 4 | 4 | 4 | 10日 | 短期月次（CLI --mode monthly 短期間）も安全 |
| 30日・契約なし | 8 | — | 8 | 22日 | 従来挙動を維持 |

### 指摘5: per_chunk_time の予算抑制（monthly.py）

```python
chunks_n = max(len(day_chunks), 1)
waves = chunks_n if parallel_workers <= 1 else max(1, (chunks_n + parallel_workers - 1) // parallel_workers)
budget_per_wave = max(remaining_budget // waves, 10)
per_chunk_time = max(remaining_budget // chunks_n, 10, min(20, budget_per_wave))
```

| 場面 | 挙動 | 理由 |
|------|------|------|
| 並列 workers=4・7日 | 20秒（下限維持） | 2波×20秒+Stage1 で予算60秒に収まる。K4 収束の維持 |
| 直列7日 | 下限は予算に応じて 10 秒程度まで抑制 | 下限20×7=140秒が予算45秒を3倍超えるのを防止 |
| 月次30日・4ワーカー | 約11秒/チャンク | 8波×11+Stage1 で 120秒に収まる |

### 指摘7: pass_budget_sec の分離（solver.py / __main__.py）

`solver.py:2262` を `stats["pass_budget_sec"] = limit_sec` に変更し、
`stats["budget_sec"]`（全体予算、初期値で常時設定）は上書きしない。
`__main__.py` の CLI 警告は `pass_budget_sec` を参照する
（現状は `budget_sec` が常に非 None のため**警告が毎回表示される**バグが同時解消）。

### 指摘8: 定数参照の完全化（weekly.py）

- `chunk_size=config.WEEKLY_CHUNK_SIZE` を `solve_monthly_hierarchical` に明示渡す。
- `parallel_workers <= 0` で `max(1, (os.cpu_count() or 2) - 1)` に自動化
  （`config.WEEKLY_PARALLEL_WORKERS=0` のコメント「0=自動」と実装を一致させる）。

### 指摘11: inf / kHighsInf の除外（monthly.py / scripts/bench_kpi.py）

- monthly.py 並列・直列両ループの `chunk_gaps` 追加時に

## 6. 残課題（将来、本計画の対象外）

- **K1（BLOCKER 0件）**: 月次階層エンジンに `solve_shift` の 2パス目（罰変数化）を適用する。
  修正後も月次/週次で需要ギャップが法令違反として残る可能性が高い（docs/15 付録C-2 に記録済み）。
- **Stage 1 の status 無視設計**: `_solve_stage1_daily_patterns` はソルバーの status を
  無視して varValue を読むため、実行不可能時は全員 OFF を返す（今回の指摘1がその一例）。
  手動確定（duty=1 固定）と公休目標が理論上衝突する組合せ（例: 7日中7日手動勤務）でも
  同様に全員OFFになりうる。status を検出して明示的なエラー/フォールバックにする価値がある。
- 指摘12（誤報正規化の閾値1e-9）・指摘13（pulp API 互換性）は確認の結果、修正不要。
