#### 実装手順

1. `src/shiftai/ui` 以下を AST で走査し、`st.<widget>(...)` の `key=` を収集する
   （本作業は WP-10 のガードテストの初回実行で機械化できる。下のテスト T2 を先に書き、
   逸脱リストを見ながら登録を進める、の順で進めるのが安全）。
2. 上表のリテラルキーを `WIDGET_KEYS` に追加する。
   `state.py:162` の集合に、区分コメント（「タブの日付・モード選択」等）を付けて追記する。
3. 動的キーは次のいずれかの方法で扱う。
   - 固定集合に展開して登録する（`sample_seed_{kind}` は kind の集合を定数化して登録）。
   - 可変長（`pattern_*_{i}`）は `WIDGET_KEYS` ではなく
     `reset_all()` 側で「接頭辞ベースの pop」を追加する。
     実装は `state.py` の `reset_all()` に
     `WIDGET_KEY_PREFIXES: tuple[str, ...] = ("pattern_start_", "pattern_end_", "pattern_name_")`
     を追加し、`st.session_state` のキーを走査して前方一致分を `pop` する。
4. 既定値の扱いを決める。
   - 「ウィジェットが自分の index / value 既定値で再生成される」だけで十分なものは
     `WIDGET_KEYS` のみに登録する（`DEFAULT_KEYS` に載せない）。
   - 「再生成後も明示的な既定値が必要なもの」（例: `monthly_holiday_target` の 8、

     理由: `DEFAULT_KEYS` に載ると `reset()` が代入を選択し、
     ウィジェット描画後に `StreamlitWidgetAlreadyInstantiatedError` で
     初期化が中断する（`state.py:172` のコメントで過去に踏んだ罠）。
     既定値はウィジェット定義側（`value=` / `index=` / `session_state.get` の既定引数）の
     一箇所に書く。
5. `KEY_MODE`（wizard）は wizard 自身が所有し wizard 内で初期化するため除外する。
   除外理由を `WIDGET_KEYS` のコメントに残す。

### WP-2: 月次モードへの `standard` / `weights` の渡し（P0）

#### 背景と該当箇所

`MonthlySolveContext` は `standard` と `weights` フィールドを持つ
（`monthly.py:66-68`）。月次求解本体も `context.standard` を
スコア（`monthly.py:556` の `compute_shift_score(..., standard=context.standard)`）、
必要人員の種別判定（`monthly.py:357-383`）、
ギャップ分析（`monthly.py:410`）で正しく参照している。

しかし**生成側の 2 箇所のどちらもフィールドを渡していない**。

- CLI: `__main__.py:554` の `MonthlySolveContext(...)` — `standard` も `weights` も未渡し
  （週モードは `__main__.py:613` で `standard=standard` を渡している）

結果、月次モードでは `standard=None` が既定になり、
`score.py` の `SHORTFALL_QUALIFIED` 再計算などが必要人員の資格定義

UI の重みスライダーも月次モードでは無視される。

#### 実装手順

1. `__main__.py:554` の `MonthlySolveContext(...)` に `standard=standard` を追加する。
   CLI に重みオプションが無ければ `weights` は渡さない（既定のまま）。
   その場合、CLI に重みオプションが無いことが意図である旨を
   `__main__.py` の該当行のコメントに残す。
2. `tab_solve.py:112` の `MonthlySolveContext(...)` に
   `standard=state.current_standard()` と `weights=weights` を追加する。
3. `monthly.py` 側は既に `context.standard` / `context.weights` を参照しているため変更不要。
   `weights is None` のときの既定フォールバックが `monthly.py` 側に存在することを確認する

4. docs 記載: 月次モードでも施設基準（プリセット）が有効であることを
   `docs/05_開発ガイド.md` の CLI 表注記、または `docs/02_ソルバ仕様.md` の月次節に 1 行追記する。

### WP-3: 認可外保育士比率の単一ソース化（P1・法解釈必要）

#### 背景

同じ「認可外保育施設の保育士比率」が 2 箇所で別値に定義されている。

- `local_rules.py:417` — プリセット「認可外保育施設（指導監督基準）」の
  `min_qualified_ratio = 1.0 / 3.0`（指導監督基準 第1(2) の「3分の1以上」に対応）
- `compliance.py:239-247` — `qualified_ratio_required()` が
  施設種別に応じて `0.75`（保育事業者型かつ定員 20 名以上）または `0.5` を**直書きで返す**。
  単独認可外・企業主導型の一部はここでは 0.5 だが、
  local_rules 側の指導監督基準プリセットは 1/3 であり、
  **どちらの経路で判定するかで結論が変わる**。

`local_rules.py:539` の説明文は「3分の1以上」、`local_rules.py:541` は
「保育士は半数以上」と書き分けており、制度ごとの差異は文中にだけ存在する。

#### 判断待ち（人間）

- 指導監督基準（単独認可外）の比率: 1/3 でよいか
- 企業主導型保育事業（単独枠）: 半数以上でよいか
- 保育事業者型事業（定員 20 名以上）: 4 分の 3 以上でよいか
- 共同利用枠の扱い（`is_shared_operator and capacity >= 20` の分岐）は正しいか

一次資料（認可外保育施設指導監督基準 令和6年3月29日こ成保第206号、
企業主導型保育事業費補助金実施要綱）で確認し、
結論と出典を `docs/03_配置基準と自治体ルール.md` に記録する。

#### 実装手順（判断完了後）

1. 単一ソースを決める。推奨は **local_rules の `StaffingStandard.min_qualified_ratio` を正**とし、
   compliance は「施設種別 → プリセット key → `local_rules.get_standard(key)`」
   経由で比率を取得する（`compliance.py` の `standard_for()` は既にこの経路を持つ）。
2. `compliance.py:246-247` の数値リテラルを削除し、
   standard からの導出に置き換える。判定不能な制度（`standard_for()` が
   `ValueError` を出すケース）では `None` を返す既存契約を維持する。
3. 保育事業者型の 0.75 を含む制度差は、対応するプリセットへ移す
   （プリセットが無いなら、判定不能として `None` を返し、
   チェックリスト側で「判定できない」と表示する）。
4. `docs/03_配置基準と自治体ルール.md` に「比率の単一ソースは local_rules、
   compliance はそこから参照する」と構成を追記する。

#### 背景

README 内部でも記述が分かれている。

  独立した最適化タスクとして分割できる。
- (b) **環境依存の明示化**: HiGHS が無い／低速環境では skip にする。
  skip の条件と理由をテストの docstring に明記する。
  これは「テストの弱体化」ではなく「測定不能な環境の宣言」であり、
  skip 条件が実際の環境を過剰に覆わないことを確認のうえ採用する。
- (c) **ベンチの相対化**: 絶対秒数のアサーションを
  「ベースライン比の倍率」に変更する。アサーション変更のため承認必須。
